# Independent handoff review — 2026-11-20

## Scope of this review

The source is the user-provided `mfem-scientific-agent.zip`, together with the original Chinese project plan and Claude's written status report. This review inspected the archive and source files, reran the Python tests on a separate environment, and checked selected artifacts. It did **not** independently compile MFEM or rerun the C++ convergence studies. Claude's reported MFEM numerical results are attributed to Claude until reproduced on another machine or CI runner.

## What has actually been implemented

- `cpp/`: a serial MFEM Poisson manufactured-solution solver with fixed reviewed cases and fault-injection paths.
- `sciagent/`: typed schemas, capability rules, environment discovery, bounded process execution, immutable-on-attempt problem/policy/validation specs, state-machine decisions, and run logs.
- `verifier/`: independent Python geometry/basis/integration/reference solve, boundary-condition checks, convergence gates, and typed verdicts.
- `specs/`: positive, negative, unsupported-configuration and bounded-retry cases.
- `tests/`: 96 test cases according to Claude, covering unit and binary-dependent integration tests.
- `docs/RESULTS.md`: run summaries including mesh-dependent errors, convergence estimates, and negative tests generated by Claude's run artifacts.

This is an engineering proof of concept, not yet a general-purpose autonomous scientific solver. No LLM planner, CAD, generic PDE compiler, distributed MPI path, GPU, or HPC scheduler is part of this MVP.

## Specific strengths

1. A real C++ numerical path is separated from deterministic orchestration and independent verification.
2. Source checks refuse unspecified/ambiguous boundary data and tested-invalid solver combinations.
3. Frozen input and acceptance policy are rehashed before each retry and not automatically relaxed.
4. Failure injection includes solver misreporting, wrong source, NaNs, boundary labeling, and early stops.
5. The manufactured-solution benchmark has plausible classical orders: L2 approximately 2 and H1-seminorm approximately 1 for P1 smooth Poisson.
6. The project preserves build/provenance metadata and supports re-verification from stored artifacts.

## Critical limitations and corrective actions

| Priority | Limitation | Required next action |
|---|---|---|
| P0 | Reported MFEM integration tests have not been repeated independently in this handoff environment | Rebuild the pinned MFEM version, run the full test suite, record a distinct reproducible environment |
| P0 | Checkpoint/verdict evidence uses local hashes and files, not a remote signed append-only audit trail | Add manifest integrity verification and artifact tamper tests; document the trust model |
| P0 | The solver and verifier still share the specification, discretization choice and mesh-producing path | Build adversarial spec/method mutation tests and distinguish implementation verification from physical validation |
| P0 | A few injected faults do not establish a reliable verifier false-accept rate | Construct systematic mutations, sample across mesh/BC/solver configurations and report denominators and confidence intervals |
| P0 | Reproducibility currently depends on Linux and nontrivial MFEM compilation, with no clean CI matrix | Add GitHub Actions for Python smoke tests and a pinned integration CI path, caching external dependencies when safe |
| P1 | Limited to two hard-coded exact solutions and unit-square mesh | Add a safe restricted expression/DSL compiler with code generation and separately compiled checker formulas |
| P1 | Boundary checking assumes known axis-aligned unit-square geometry | Introduce named boundary labels via Gmsh, tolerance-aware geometry checks and independent mesh validation |
| P1 | The compatibility matrix applies only to a tested serial subset | Add MPI + hypre + METIS as an explicit new capability with serial-parallel comparisons |
| P1 | Error tolerances may become brittle outside regular meshes | Make thresholds dimensionally and numerically justified; test curved, distorted and coarse meshes without silently relaxing criteria |
| P2 | No LLM-driven planning layer yet | Only after deterministic false-accept/verified-completion baselines, expose audited tool selection from a reviewed allowlist |

## Suggested objective evaluation metrics

- Verified completion rate across a versioned benchmark suite, not just process exit status.
- False-accept fraction, estimated over documented injected faults and mutations, with confidence bounds.
- False-reject fraction on known-correct reference implementations and supported configurations.
- Numerical error and observed convergence orders under predeclared acceptance bands.
- End-to-end total wall time, iterations, energy/resource cost, and retries per accepted result.
- Exact reproducibility of verdicts and integrity of stored evidence.

## Scope control

Preserve the deterministic vertical slice. Do not replace it with ten LLM agents. First achieve clean local reproduction + CI + systematic verifier challenge. Then add constrained equation generation, real meshes, MPI, a second PDE family, and optional LLM planning. Every new capability must add a validation method and a capability-matrix entry.

## Evidence policy

The original ZIP contains ~1,800 entries and large generated solver binaries/mesh/DOF dumps. Those are not source code and should not be copied wholesale into Git history. `docs/RESULTS.md` and a curated `evidence/` subset are retained, while the user's original ZIP remains the raw archive if exact historical reproduction is required. Full run datasets should be handled as release artifacts or external storage, with cryptographic checksums.
